# Read-only Windows Sandbox capability probe

> **Current safety freeze (audit §211):** `ScopedNetworkWfpSmoke.ps1`, `UserSidChromiumSmoke.ps1`, and the default WFP mode of `AppContainerIdentitySmoke.ps1` now stop before any WFP call. The C# BFE mutation probe, host wrapper, guest PowerShell runner, and CMD runner are also disabled. Procedures and results below that describe these mutating probes are historical; do not run their old commands or start a Sandbox from them. `CapabilitySmoke.ps1` is a separate read-only query. `AppContainerIdentitySmoke.ps1 -ChromiumOnly` skips the WFP branch and remains a diagnostic mode.

The `.wsb` files mentioned below are machine-local launch profiles with host-specific folder mappings. They are intentionally ignored by Git and are not included in the source release; a clean checkout does not contain them. Keep any local profile's mappings read-only except for the dedicated results folder, and do not treat a historical profile as an authenticated Sandbox controller.

This disposable probe checks whether a fresh Windows Sandbox guest can query its administrator token, Base Filtering Engine (BFE), and WFP filter enumeration API. It does not install software, create a WFP session with write access, or add/remove filters.

`ReadOnlyWfpSmoke.wsb` disables guest networking, mounts this directory read-only, and mounts the sibling `sandbox-results/` directory as the only writable host folder. After the host has restarted and Windows Sandbox is confirmed enabled, open the `.wsb` file. The guest runs `CapabilitySmoke.ps1` automatically and writes `sandbox-results/wfp-capability-smoke.json`.

The report is only a capability smoke check. It does not prove filter structure validity, arbitration, egress isolation, or service/installer behavior. Delete the generated result after reviewing it if it should not remain in the worktree.

## Latest local run

On Windows 11 Enterprise LTSC build 26100, both the default guest account and a SYSTEM process opened the engine with `RPC_C_AUTHN_WINNT` (10), created a filter-enumeration handle, and read one filter. `RPC_C_AUTHN_DEFAULT` (0) returned Win32 50 in both contexts. A guest SYSTEM `netsh wfp show state` export also succeeded. The first probe version used a managed `string` for the optional server name and failed; the corrected declaration uses `IntPtr` and passes `IntPtr.Zero` for native NULL. The observations establish only read-only query capability. Networking is disabled in this `.wsb`; no filter was added/deleted and no network enforcement behavior was tested.

## Dynamic smoke

`NetworkWfpWriteSmoke.ps1` is retired and fails before loading native code or opening BFE. `ScopedNetworkWfpSmoke.ps1` is now also disabled before its dynamic WFP session and filter-add calls. Their earlier guest-only results are historical; they are not a reason to run the scripts on a host. The C# materializer's BFE probe and wrapper are disabled as well. Re-enablement requires an independently authenticated guest boundary and a new review; no runnable BFE wrapper is currently provided.

## AppContainer identity prerequisite

`AppContainerIdentitySmoke.ps1` refuses its default WFP mode before profile creation or network probes. The old `.wsb`/CLI procedure is retired; do not use it to start a Sandbox. Its prior guest-only WFP behavior below is kept as historical evidence. The explicit `-ChromiumOnly` mode bypasses that WFP path and is a separate browser diagnostic.

The earlier WFP version created two unique AppContainer profiles, started native `curl.exe` children with network capabilities in both, verified each child's token package SID, and checked that loopback was denied before a profile-specific `CheckNetIsolation` exemption and accepted afterward. It then confirmed both profiles could reach the same pinned IPv4 HTTPS endpoint, opened a dynamic WFP session, and added a temporary IPv4 ALE connect block matching `FWPM_CONDITION_ALE_PACKAGE_ID` for the first profile SID. That historical guest result is recorded in the audit report; the write path is now disabled because the script itself cannot attest that it runs inside Sandbox.

An optional -ChromiumPath parameter accepts a mapped chrome.exe. The probe stages the complete containing directory in guest-local temporary storage, grants the test AppContainer SID read/execute access on every existing staged file and directory, and gives the SID a separate writable user-data directory. It tries --version and, only when explicitly requested, a headless about:blank launch. This is diagnostic only. In the latest network-disabled Sandbox run, ExistingLogin was active as WDAGUtilityAccount in session 1. The explicit ACL removed Chromium's earlier executable AccessCheck error, but both --version and --no-sandbox --version failed at Crashpad CreateNamedPipe with access denied (0x5), then exited STATUS_BREAKPOINT. Stderr and Application Error/WER events were captured; no dump was collected and the headless page was not run. The [exact locked Chromium `crashpad_client_win.cc`](https://github.com/chromium/chromium/blob/971a7443b0c9b0a9b2860529b33331b76077ec62/third_party/crashpad/crashpad/client/crashpad_client_win.cc#L298-L323) uses a `LOCAL` pipe only under `WINDOWS_UWP`; its ordinary desktop branch creates a non-LOCAL pipe. This is consistent with an AppContainer namespace restriction but does not identify whether the failing call is the browser-side client or Crashpad handler, or prove the cause. Do not apply a blanket `LOCAL` name change without runtime evidence. See audit report §114 and the ignored results chromium-appcontainer-acl.json / chromium-appcontainer-no-crashpad.json. This does not establish full process-tree coverage or production isolation; --no-sandbox is not a product workaround.

`ChromiumContextBaseline.ps1` is a companion `--version` comparison and does not launch a page. Its context and timeout behavior are recorded in the result JSON. `ChromiumDiagnostic.wsb` is the network-disabled profile for an interactive-session baseline and user-parent AppContainer diagnostics; connect to its desktop before invoking `wsb exec --run-as ExistingLogin`. The existing identity/WFP smoke profile still requires guest SYSTEM and networking, and should not be used as the network-disabled Chromium diagnostic.

The probe also does **not** test a service/IPC/installer, persistent deny, IPv6/UDP policy, filter arbitration with production providers, or complete browser process-tree coverage. A WFP/AppContainer pass validates only the prerequisite on this Sandbox build; it does not close P2. The CLI run stops the Sandbox in `finally`, discarding the filters, profiles, and loopback exemption. Never run this probe on the host.

## Chromium AppContainer diagnostics

ChromiumDiagnostic.wsb provides a separate guest with networking disabled. It maps the locked Chromium 1243 directory read-only, the probe scripts read-only, and only the local results directory writable. Use it to compare Chromium under an interactive Sandbox login and an AppContainer child; do not use this network-disabled profile for the curl/WFP Internet baseline smoke. Connect to the Sandbox desktop before invoking wsb exec --run-as ExistingLogin, because that run-as option requires an active guest user session. Keep crash dumps and event diagnostics inside the disposable guest or mapped results directory, and delete them after review. The latest result and current limitation are summarized above and in audit report §§114–115.

## Per-user SID WFP and interactive Chromium follow-up

`UserSidChromiumSmoke.ps1` is disabled before account creation, browser staging, or WFP setup because its guest-only assumption is not independently verified by the script. The previous `ChromiumUserSidSmoke.wsb` result is historical and is not a runnable validation procedure. It created a random low-privilege local user, staged Chromium, and tested a dynamic user-SID block; that test did not establish production isolation.

The curl subtest passed in §115: engine open, sublayer/filter add, and close returned 0; user curl was blocked, SYSTEM curl remained allowed, and the user connection recovered. The credential-created Chromium process did not complete before or during the filter. A separate network-disabled interactive user smoke used `StageChromiumForInteractiveUser.ps1` to copy the 308-file tree and grant user/package read/execute on 317 items, then ran `ChromiumInteractiveHeadlessSmoke.ps1`. It timed out after 20 seconds without an about:blank screenshot; the log contained DNS-config warnings and GPU virtualization context errors. The first result exposed an unsupported `Process.Kill(true)` overload. The updated script now tracks descendants from the launched root PID within the staged browser directory and emits stopped/remaining PID lists. A follow-up Sandbox run confirmed that the root and nine children were stopped and `remainingProcessIds` was empty, but the screenshot was still absent and overall status remained fail. This verifies cleanup only, not Chromium startup, page rendering, a proper service-managed user-session token, or browser egress. The WFP rule was only tested with curl. The environment was stopped and `wsb list --raw` was empty; host WFP/Firewall was untouched. See audit report §116 and ignored results `chromium-user-sid-wfp-smoke.json`, `chromium-interactive-acl-baseline.json`, and `chromium-interactive-headless.json`.

## CreateProcessAsUser Chromium session diagnostics — disabled

ChromiumAsUserTokenSmoke.ps1 and GrantInteractiveDesktopAccess.ps1 now fail immediately before writing results, creating accounts or directories, copying Chromium, changing file or desktop ACLs, launching processes, or running cleanup. The previous SYSTEM-SID check, interactive-session fields, and JSON RunToken handshake did not prove that either process was inside a disposable Windows Sandbox; running them on the host could modify host state.

Do not use the former wsb exec procedure. The §117 Chromium measurements are historical diagnostics only and do not establish current Sandbox isolation or product acceptance. Re-enable these probes only after a trusted host controller supplies a guest-bound, one-time attestation over a protected channel and failure handling is independently verified.
## C# materializer to BFE integration probe

**Disabled. Do not run this probe or its wrapper.** The earlier probe treated a GUID, caller-controlled environment variables, and the SYSTEM SID as if they proved Windows Sandbox identity. They do not. A SYSTEM process on the host could forge those values and reach persistent BFE writes.

The test executable no longer exposes `--sandbox-bfe-smoke` or `--sandbox-probe-client`. The old BFE writer was removed, and both BFE mutation and network probe entry points now return code 2 with a disabled message. `RunMaterializerBfeSandboxSmoke.ps1` throws immediately before creating result directories or starting a Sandbox. The former environment/token and SYSTEM checks were not an attestation and cannot authorize network probes.

The ordinary offline policy/materializer harness remains available and does not apply policy. From the repository root, build and run the test harness with the project-pinned .NET SDK. Its direct-entry regressions verify that the disabled BFE and network probe commands reject calls, including when the caller supplies the old guest environment marker and run token. This does not test BFE/WFP behavior, create a Sandbox, or modify host firewall policy.

Re-enablement requires a separately reviewed trust boundary that proves the guest was created by the current host wrapper and cannot be forged by a host SYSTEM caller. Until that exists, leave the write probe disabled; historical implementation and test limitations are recorded in `docs/PROJECT_AUDIT_REPORT.md` §§195–211.
