# WFP policy plan and managed layout preview

> **Scope warning (2026-10-11):** This AppID-based preview predates the AUD-86 lease-boundary review. It does not model unique per-lease OS identities, a catch-all deny for other local clients to the listener, the service-owned CONNECT relay, or restricted service-side upstream egress. It is a non-deployable historical construction preview, not the current WFP service specification. Those production requirements remain unimplemented; do not implement or deploy these preview rules as a complete isolation policy.

This x64 .NET project is a review artifact for the P2 isolation work. It emits:

- `--plan`: a validated **semantic** description of the intended policy (protected browser identity; only the broker-owned TCP `127.0.0.1:<lease-port>` endpoint; deny other IPv4/IPv6 destinations).
- `--filter-plan`: a typed **construction preview** with the WFP condition identifiers, comparison operators, value types, action values, flags, and relative weights for the five intended filters.
- `--layout`: `Marshal.SizeOf` and `Marshal.OffsetOf` values for CsWin32-generated WFP structures in the running x64 .NET process.

The sample path, port, and browser protection state are illustrative. The plan is intentionally marked `not-deployable`. The IPv4 complement is represented by three separate mismatch filters: non-TCP protocol, remote address other than `127.0.0.1`, and remote port other than the active lease port. WFP requires all conditions in one filter to match (AND), so one filter cannot express “any component differs” as a single condition. The exact permit must have higher weight than these blocks in the same sublayer; IPv6 remains default-blocked. The intended exception is a soft permit, so a block from another sublayer continues to win under WFP's arbitration rules.

## Safety boundary

This executable has no command that applies a plan. Its command allowlist is only `--plan`, `--filter-plan`, `--layout`, and `--help`; unknown arguments fail closed. The C# executable has no WFP API imports or BFE session creation, no service entry point, no installer, and no code that changes firewall, registry, or OS policy. `NativeMethods.txt` requests WFP structure declarations and condition identifier constants, not callable APIs. Running it as Administrator adds no functionality and is unnecessary.

## Per-lease policy compiler source slice

The pure managed compiler and its input/plan types live in the `WfpPolicy.Core` library. It has no CsWin32 dependency or WFP calls and models the current control-plane/worker/lease rules. The CLI and native construction-preview project reference this library; it does not change the historical `--plan` or `--filter-plan` output and does not rewrite `artifacts/native-filter-plan.example.json`. Production service code must depend on a future high-level runtime facade, not on this plan/compiler assembly.

The service-owned input consists of a non-empty lease UUID, an explicit user-SID or AppContainer-package-SID principal kind, the lease SID, browser and worker AppID byte blobs encoded as hex, a unique loopback listener port, a numeric public resolver address, and the complete already-validated public A/AAAA address set for that lease. The compiler rejects duplicate lease IDs, SIDs or listener ports, browser/worker AppID overlap, malformed identities, non-numeric/scoped addresses, and non-public resolver or pinned targets. User SIDs are limited to canonical local-account shapes. A non-built-in package SID must have the eight App Package RIDs (`S-1-15-2` plus seven package-derived RIDs), following Microsoft's `SECURITY_APP_PACKAGE_RID_COUNT`; this validates syntax/cardinality only. The service must still derive or obtain the SID from Windows and compare it to the actual process token. The compiler sorts normalized addresses, leases and rules so the same inputs produce byte-stable JSON when serialized with the same serializer options.

Each compiled document retains persistent IPv4/IPv6 catch-all blocks for every protected browser and worker AppID. The unique lease principal (`ALE_USER_ID` or `ALE_PACKAGE_ID`) receives IPv4/IPv6 catch-all blocks only in that lease's dynamic session, together with the exact listener block and permits. This avoids persistent per-lease SID filters accumulating after normal completion or a service crash. It is safe to deploy this split only after the service launches every browser/worker descendant into a non-breakaway Job Object with `KILL_ON_JOB_CLOSE`, proves the complete process tree is gone before closing the dynamic session, and establishes/reads back the persistent AppID baseline before accepting any lease. Those lifecycle controls are not implemented here.

The source now also uses internal, constructor-controlled plan types: `PersistentAppIdBaselinePlan`, `DynamicLeasePlan`, and `ServiceWideLeasePolicyPlan`. `CompilePersistentAppIdBaseline` accepts browser/worker AppIDs only and rejects a missing role, duplicate entry, or identity reused across roles. `CompileDynamicLease` accepts one lease and emits only that SID's dynamic catch-all, listener block, and exact permits. The service-authoritative `CompileServiceWidePlan` compiles a baseline and the full active lease set together, checks each browser and worker AppID against the matching protected role, and rejects duplicate lease identities/ports. The separate compiler methods remain internal building blocks and must not be used to compose a production service plan independently. Type-specific inspection entry points reject rules with the wrong lifetime before building any structures. The older aggregate semantic document remains for review compatibility; none of these APIs applies policy or verifies the input executable path.

The principal-wide dynamic blocks have no AppID, address, protocol, or port condition, so an arbitrary helper/child executable carrying that lease principal has no permit while the session is active. Exact exceptions still require the matching browser/worker AppID and lease principal. This is a token-identity boundary, not process ancestry tracking: a child is covered only when its actual network token carries the unique lease identity, which the service must verify at launch and during lifecycle management. Live validation must inspect the created process-tree tokens and the effective IPv4/IPv6 WFP filters and arbitration on supported Windows versions; the compiler test does not establish that those filters match the intended token fields or cover every flow. Lease-dynamic rules also block other local clients from the exact IPv4 loopback listener, then permit only the matching browser identity to reach that listener over TCP. The matching worker identity receives only TCP/UDP port 53 to its numeric resolver and TCP/443 to that lease's listed pinned addresses. The output uses soft actions and range-index weights (default block 1, exact lease permit 15) as semantic intent for one future service-owned sublayer. It is always `not-deployable` and leaves identity provenance, actual filter construction, BFE behavior, external-provider arbitration, DNS-answer completeness, token verification, worker lifecycle and rollback unresolved.

The no-network policy compiler harness has no NuGet test-framework dependency and does not access Windows policy APIs:

```powershell
dotnet run --project tests/LeasePolicyCompiler.Tests.csproj --configuration Release
```

It checks two-lease cross-access, exact listener/DNS/upstream constraints, persistent AppID-wide plus dynamic principal-wide IPv4/IPv6 default-deny coverage, typed-plan lifetime separation, service-wide AppID-to-role binding, rejection of forged private/arbitrary-port permits, deterministic output, both supported SID-condition encodings, duplicate/cross-role identities, malformed inputs, private/special address rejection, and the permanent `not-deployable` label. The current harness passes **14/14**. These are compiler/materializer tests only. They do not prove WFP filter semantics, service installation, Job Object containment, actual child-token identity, Chromium identity, DNS pinning behavior, or network isolation.

## In-memory native filter materializer

`WfpFilterMaterializer` is an internal Windows-only source slice; external assemblies cannot call it with a caller-constructed `LeasePolicyDocument`. It converts a bounded, permanently non-deployable document into CsWin32 `FWPM_FILTER0` and `FWPM_FILTER_CONDITION0` structures in a temporary unmanaged arena. It copies the fields into a pointer-free review result, zeroes and frees the arena, and returns `PolicyMutated = false`. It has no WFP API calls, BFE session, service entry point, apply command, or escaping native pointer. Its provider and sublayer GUIDs must be explicit and non-empty.

The materializer maps AppID to `FWP_BYTE_BLOB_TYPE`; `ALE_USER_ID` to a self-relative security descriptor with only the `FWPM_ACTRL_MATCH_FILTER` allow ACE; AppContainer package identity to `FWP_SID`; IPv4 remote addresses to host-order `FWP_UINT32`; IPv6 addresses to `FWP_BYTE_ARRAY16_TYPE`; protocol to `FWP_UINT8`; port to `FWP_UINT16`; weight range index to `FWP_UINT8`; and persistent default-deny lifetime to `FWPM_FILTER_FLAG_PERSISTENT`. IPv4 dotted-address bytes are interpreted as a big-endian number for the host-order WFP value: `127.0.0.1` maps to `0x7F000001`, and `93.184.216.34` maps to `0x5DB8D822`. The inspection snapshot includes both the readable address and `RawUInt32Value`, and the harness asserts both so a round-trip conversion cannot hide an incorrect native integer. Microsoft documents the host-order requirement in [`FWP_V4_ADDR_AND_MASK`](https://learn.microsoft.com/en-us/windows/win32/api/fwptypes/ns-fwptypes-fwp_v4_addr_and_mask) and permits `FWP_UINT32` for IPv4 address conditions in the [filtering condition data types](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/filtering-condition-data-types).

The materializer rejects unknown identity forms, non-canonical/scoped addresses, malformed SIDs/AppIDs, empty provider/sublayer IDs, unsupported action-right clearing, and plans that do not remain explicitly non-deployable. It also validates the full dynamic permit kind and fields: browser permits must target the exact loopback listener, DNS permits must use the public numeric resolver on TCP/UDP 53, and upstream permits must use a listed public numeric destination on TCP 443; each lease must contain the complete consistent rule group. Condition GUIDs come from the pinned CsWin32-generated declarations, including `ALE_USER_ID` and `ALE_PACKAGE_ID`. Filter members and conjunction behavior are documented in [`FWPM_FILTER0`](https://learn.microsoft.com/en-us/windows/win32/api/fwpmtypes/ns-fwpmtypes-fwpm_filter0).

The harness checks these native field mappings, SID descriptor contents, unique stable filter keys, IPv4/IPv6 round trips, action/weight/lifetime values, and rejects ambiguous or deployable-looking input. It is still a structure-construction test: it does not prove that BFE accepts the structure, that a persistent or dynamic session behaves as intended, that conditions are available at the selected layer on every supported Windows build, or that any filter is active. The current CLI commands do not invoke this materializer; the Sandbox WFP builder also remains separate.

`--filter-plan` emits a non-deployable construction preview. It makes each rule's `FWPM_CONDITION_*` field key, `FWP_MATCH_*` operator, `FWP_*` value type, action, filter flags, and weight explicit. Its validator compares every rule and condition against the expected layer/GUID, action, flag, weight, operator, type, and constant value. The checked-in `artifacts/native-filter-plan.example.json` is generated from this command (current SHA-256 `51bf789b93e250a431b4c0ca756b4b86ad69d0a161a02bb561fd51a2a6553f0d`). The weights use `FWP_UINT8` range indices from 0 through 15 (the exact permit preview uses 15; mismatch blocks use 1), not literal 8-bit filter weights. Four hard-block rules express the IPv4 mismatch deny set and IPv6 default deny; a fifth soft permit expresses the illustrative exact proxy endpoint. Filter/sublayer keys are placeholders, the AppID blob is not serialized, and the example port is not a live lease. The `--filter-plan` CLI command does not invoke the in-memory materializer, open BFE, or install any object.

The included PowerShell files are development diagnostics, not a sandbox boundary, and they do not verify that they are running inside Windows Sandbox. `ChromiumInteractiveHeadlessSmoke.ps1` starts Chromium as the caller; `AppContainerIdentitySmoke.ps1 -ChromiumOnly` stages a Chromium copy, changes temporary ACLs, and adds/removes an AppContainer loopback exemption; `ProcessSingletonApiProbe.ps1` creates temporary OS objects and a lock file and can optionally start Chromium. None of these actions proves network isolation. Run diagnostics only in a disposable, controlled Sandbox. Their output can contain SIDs, user names, and local paths; keep reports and screenshots there.

An older unrestricted WFP write probe has been retired. The available mutation entry point is a fail-closed stub and performs no BFE call. Results collected before it was disabled are historical and do not show that the current entry point can run.

`sandbox/ScopedNetworkWfpSmoke.ps1` is currently disabled: it throws before any BFE call until the Sandbox guest boundary can be independently authenticated. A previous Sandbox result predates this fail-closed entry point and is historical evidence only; it does not show that the current script is runnable. That older probe covered only `::1` for IPv6 and did not test Chromium, a project service/lease, persistent default-deny policy, other providers, or production isolation. The script must remain disabled until its guest boundary is independently authenticated.

The CLI prints JSON to standard output. It does not query whether WFP isolation is active. Earlier Sandbox probes exercised bounded guest-only WFP operations using a separate helper and do not establish the current script's behavior. The C# CLI and that historical helper use separate native structure builders. Neither proves project-service policy, Chromium isolation, persistent default-deny behavior, or full network isolation. Do not treat this project or its output as a deployed sandbox or proof of isolation.

## Validation limits

The layout report records the managed layouts emitted by Microsoft.Windows.CsWin32 0.3.360 for x64 .NET 10. It is **not** cross-checked against `sizeof`/`offsetof` from the Windows SDK headers, since the required SDK headers/compiler are not present in the validation environment. A historical scoped Sandbox probe, run before the checked-in entry point was disabled, observed its loopback exception, wrong-port/address/protocol blocks, IPv6 block, distinct-application positive path, and dynamic cleanup for the PowerShell AppID using the pinned preview JSON. That result is not reproducible with the included disabled entry point and does not verify Chromium or external-provider arbitration. It also did not verify raw-socket/resource-assignment coverage, IPC peer authentication, service installation/ACLs, socket duplication, persistent filter behavior, crash recovery, or rollback.

Before any future service implementation, those items need independent validation in a disposable Windows VM. A historical probe using a separate helper observed that the test Sandbox accepted the `FWP_MATCH_NOT_EQUAL` `FWP_UINT32` remote-address condition and the chosen host-order loopback value for the PowerShell image. This does not prove the included preview or disabled entry point works, nor that the policy works for protected Chromium or across supported OS servicing levels. The exact endpoint exception must be proven not to override hard blocks from other providers. Conflicts with another provider's hard permit and cross-sublayer arbitration remain unresolved. The C# preview does not build `FWPM_FILTER0` values; the separate historical helper is not part of this release candidate, and neither path claims production enforcement.

## Build and preview

The local .NET SDK is pinned in `global.json`; NuGet package versions are pinned in `packages.lock.json`:

```powershell
dotnet restore --locked-mode
dotnet build --no-restore --configuration Release
dotnet run --no-build --configuration Release -- --plan
dotnet run --no-build --configuration Release -- --filter-plan
dotnet run --no-build --configuration Release -- --layout
.\VerifyFilterPlanArtifact.ps1 -DotNetPath (Get-Command dotnet).Source
```

The verifier regenerates `--filter-plan`, compares it byte-for-byte with the checked-in JSON, and checks that the Sandbox script's SHA-256 pin matches. The earlier, enabled guest smoke implementation performed an independent field-level allowlist check before WFP writes; the checked-in entry point is now a fail-closed stub and performs neither that check nor any WFP write.
